## 一、需求评审（Review）

### 1.1 总体评价

文档结构清晰、覆盖面合理：技术栈、三层架构、8 大功能模块、MySQL/Redis 数据模型、REST + WebSocket 双协议接口、非功能指标都齐备，作为一版初稿是**可落地的**。核心链路（注册 → 加好友 → 单聊 → 在线/未读/已读/图片）逻辑自洽。

但存在 **2 个必须拍板的技术分歧**、**5 个架构/设计缺口**、若干安全与功能边界问题。下面按严重程度分级。

---

### 1.2 必须决策的关键分歧（Blocker，不解决无法开工）

| 编号 | 问题 | 建议 |
|------|------|------|
| **B1** | 后端"Node.js(NestJS) **或** Spring Boot 二选一"，WebSocket 也跟着二选一。这是贯穿全栈的底座决策，文档未定。 | **推荐 NestJS + Socket.IO**：与前端 React/TS 同语言、迭代最快、WebSocket 生态成熟。若团队是 Java 技术栈/已有 Spring 体系则选 Spring Boot。需在 Phase 0 拍板，否则脚手架无法启动。 |
| **B2** | 图片"上传至服务器**（或对象存储）**"，"或"未决。 | **推荐对象存储**（MinIO 自建 / 阿里云 OSS / 腾讯云 COS）。本地磁盘在横向扩展、CDN、备份上都是坑。MVP 可用本地磁盘，但存储层要抽象成接口，便于迁移。 |

---

### 1.3 架构 / 设计缺口（Major）

| 编号 | 问题 | 影响与建议 |
|------|------|-----------|
| **M1** | Redis 存了"所在服务器节点"，暗示多节点部署，但**没有任何跨节点消息投递机制**（怎么把消息发给连在另一台机器上的用户）。 | 非功能写的是"单节点 5000+ 并发"，所以 MVP 单节点即可，**先去掉"节点"假设**。但消息分发器要从第一天就抽象成"发布/订阅"接口：单节点直推，多节点用 **Redis Pub/Sub / Kafka** 扇出，避免将来重写。 |
| **M2** | 未读数、已读游标**只存 Redis**，未提持久化与降级重建。Redis 宕机/重启丢数据则未读数与已读状态错乱。 | Redis 开 **AOF + RDB**；并规定"Redis miss 时从 MySQL `messages` 表按 `read_cursor` 重算未读"，保持最终一致。 |
| **M3** | `users` 表有 `avatar_url`，但注册只收用户名/密码/昵称，且接口列表里**没有头像上传/更新接口**。好友搜索要返回头像，头像从哪来？ | 补一个"更新个人资料（头像/昵称）"接口，复用图片上传能力；或注册时允许带头像。 |
| **M4** | WebSocket 握手带 JWT 鉴权，但 JWT 有效期 7 天，**未提连接期间的过期处理与主动吊销**（如改密码、封禁后如何踢线）。 | WS 连接内做 token 过期检查；引入**短时效 access token + refresh token 轮换**，必要时用 Redis 维护吊销黑名单。 |
| **M5** | 好友关系存在并发竞态：重复发送请求、双方同时发起、接受/拒绝状态机未定义；无唯一约束说明。 | 表加 `(user_id, friend_id)` 唯一索引；`friend_requests` 用明确状态机（pending/accepted/rejected）；接受时幂等处理。 |

---

### 1.4 安全与健壮性（Major / Minor）

- **限流防刷**（缺）：好友请求、消息发送需限流，防骚扰与刷接口。
- **传输安全**（缺）：生产必须 **WSS（WebSocket over TLS）** + HTTPS；反向代理（Nginx）需正确配置 WS 升级。
- **CORS**（缺）：REST 需明确跨域白名单。
- **XSS**：React 默认转义，但需禁止在消息渲染中使用 `dangerouslySetInnerHTML`；富文本（若有）需白名单清洗。
- **图片上传安全**：校验大小（≤10MB）、类型（JPG/PNG/GIF/WebP）、防路径穿越；对象存储可天然规避本地路径风险；条件允许加病毒扫描。
- **JWT 刷新机制**（缺细节）：`/api/auth/refresh` 用 refresh token 轮换还是滑动会话？需明确，避免长期有效 token 被盗用。
- **SQL 注入 / 参数化**：需求里提了，落实时用 ORM 参数化查询即可，属提醒项。

---

### 1.5 功能边界与可选增强（Minor，需明示为范围决策）

- **仅单聊、无群聊**：文档未强调这是"刻意的范围裁剪"。建议显式写成"本期不含群聊"，避免歧义。
- **缺消息撤回/编辑**、**"输入中"状态**、**拉黑/免打扰**、**跨会话全局搜索**（仅会话内搜索）。
- **用户名精确搜索**：仅精确匹配，体验受限；可改为"包含+分页"。
- 以上均非阻塞，列入"二期/可选"。

---

### 1.6 非功能需求补充建议

- **可观测性**（缺）：结构化日志、健康检查（`/health`）、关键指标（在线连接数、消息吞吐、推送延迟）。
- **部署**：Docker 化、环境变量配置（密钥不入库）、Nginx 反代 WS。
- **数据备份**：MySQL 定期备份；Redis 持久化策略。
- 非功能指标（<500ms 延迟、5000+ 并发、99.5% 可用）合理，建议补充**压测方案**与验收口径。

## 二、开发计划（Plan）

### Phase 0 — 技术决策与脚手架（0.5 周）

- **决策门**：拍板 B1（后端栈）、B2（存储方案）。
- 初始化仓库：Monorepo 或前后端分离；ESLint/Prettier/CI 基础。
- 基础设施即代码：MySQL 8 + Redis 6 的 Docker Compose；`.env` 管理密钥。
- 定义跨模块契约：消息体结构、WebSocket 事件 schema、错误码。

**里程碑**：本地一条命令起全套依赖；API/WS 骨架可跑通 Hello。

---

### Phase 1 — 认证与用户（1 周）

- 注册（用户名唯一、bcrypt 哈希）、登录（签发 JWT，建议 access+refresh 双 token）。
- `refresh` 接口、WS 握手 JWT 校验（含连接内过期检查，对应 M4）。
- 个人资料更新接口（补 M3 头像/昵称）。
- 密码/输入参数校验、CORS、基础限流。

**验收**：注册→登录→持 token 建 WS 连接成功；错误凭证被拒。

---

### Phase 2 — 好友系统（1 周）

- 用户搜索（建议改为包含匹配）、发送好友请求（WS 实时通知，离线走 REST 拉待办）。
- 接受/拒绝（状态机 + 幂等，对应 M5）、好友列表（含在线状态占位）、删除好友（清缓存）。
- 好友关系唯一约束与并发处理。

**验收**：A 向 B 发请求→B 收到→接受→双方互为好友并出现在列表；重复请求被拒。

---

### Phase 3 — 实时通信核心（1 周）

- WS 网关：连接管理（连接池/注册表）、心跳（30s 发、60s TTL，对应文档）、断线重连。
- **消息分发器抽象为发布/订阅接口**（对应 M1）：单节点直推，预留 Redis Pub/Sub 扩展点。
- 鉴权失败/异常连接的优雅关闭。

**验收**：多客户端连入、心跳维持在线、异常断线可自动重连。

---

### Phase 4 — 单聊与消息历史（1.5 周）

- 文字消息发送/接收（先持久化 MySQL 再推送，对应一致性要求）。
- 消息 ID 策略（推荐雪花 ID，保证会话内单调有序）。
- 游标分页拉历史（messageId 游标、50/页）、客户端去重与排序。
- 断线重连后按最后 messageId 增量补齐离线消息。

**验收**：A 发消息 B 实时收到；B 翻页历史顺序一致、无重复；重连后补齐。

---

### Phase 5 — 在线状态 + 未读 + 已读回执（1.5 周）

- Redis 结构落地：`user:online`、`user:unread`、`user:read_cursor`（对应数据模型）。
- 上线/下线通过 `presence:update` 通知在线好友；未读 +1 通过 `unread:update` 推送。
- 打开会话清零未读 → 发 `message:read` → 对方收 `message:read_receipt` 标记已读。
- **Redis 持久化 + miss 降级重算**（对应 M2）。

**验收**：A 离线时 B 发消息，A 上线看到未读数与最后在线时间；A 打开会话 B 消息变"已读"。

---

### Phase 6 — 图片消息（1 周）

- 图片上传接口（大小/类型校验、对象存储或本地抽象层，对应 B2）。
- 缩略图生成（≤240×240）、图片消息体（原图/缩略图 URL + 宽高）。
- 客户端懒加载、点击看大图、加载失败重试。

**验收**：单聊发图 → 对方收缩略图 → 点击加载原图。

---

### Phase 7 — 非功能打磨与上线（1~1.5 周）

- 限流防刷、WSS/HTTPS、Nginx 反代、CORS 收紧。
- 可观测性：日志/健康检查/指标；MySQL 备份、Redis 持久化。
- 压测：验证 <500ms 延迟、5000+ 并发、99.5% 可用；补齐验收口径。
- 边界用例与异常流程回归。

**验收**：压测达标；安全项（JWT/bcrypt/注入/XSS/上传校验）通过自查清单。

## 三、风险与待确认清单（交给你的）

1. **[B1]** 后端技术栈最终选 NestJS 还是 Spring Boot？
2. **[B2]** 图片存本地磁盘还是对象存储（MinIO / 云 OSS）？
3. **[M1]** 本期是否只做单节点？是否现在就引入 Redis Pub/Sub 以便日后横向扩展？
4. **[M4]** 是否采用 access+refresh 双 token？是否需要"改密码/封禁即踢线"？
5. **[范围]** 本期是否明确"仅单聊、不含群聊、不含撤回/编辑"？
6. **[部署]** 目标运行环境（自建服务器 / 云）、是否需要 Docker 交付？

> 以上 6 项确认后，Phase 0 即可启动；其余 Major/Minor 问题已并入对应 Phase 的任务与验收中，不影响开工。
